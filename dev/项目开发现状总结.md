### 0.2 BT 结论反转：原「现实瓶颈」不成立

原文档的三个判断都站不住：

1. **消息 id 标错了。** `debug2.mjs` 把 id=1 打印成 `CHOKE`、id=5 打印成 `UNCHOKE`。协议里 0 是 CHOKE、1 是 UNCHOKE、5 是 BITFIELD。日志里的「CHOKE」其实是对方已经放行。
2. **`upload_only` 读反了。** 扩展握手里的 `upload_only=1` 表示对方已经下完、只做种，是最有价值的 peer，不是吸血节点。
3. **探测脚本自己有 bug，这才是真因。** `debug2.mjs` 和 `fullprobe.mjs` 发扩展握手、发 ut_metadata 请求时，消息长度前缀少算了消息 id 的 1 个字节。对端会把后面的字节吞进一条不存在的消息里，然后断连。表现就是「请求发出去了，对方也 unchoke 了，但拿不到 metadata」。

复核时我在自己写的探测脚本里犯了同一个错，一度得出「一发扩展握手就被断连」的结论。拿 Ubuntu 官方种子做对照才发现：真实客户端也一样断，说明问题在我这边。修正后扩展握手正常，ut_metadata 能取回并通过 SHA1 校验。

【实测】2026-11-25，开发机所在网络（不是手机），探测脚本 `scripts/btprobe/swarmcheck.mjs`：

| 测试 | 资源 | 结果 |
|---|---|---|
| 元数据走 HTTPS | 单集（mikan，686MB） | `.torrent` 7359 字节，0.6 秒，SHA1(info) 与 infohash 一致 |
| 完整 piece 校验 | 同上，连 8 个真实 peer | 6 个返回完整的 2MB piece 0，SHA1 与种子一致，文件头是合法 MKV |
| 吞吐 | 同上，tracker + DHT 共 121 个候选，探测 70 个 | 握手成功 42；回数据 7，其中 5 个下完 1MB；单 peer 51～261 KB/s |
| 发扩展握手 | 同上 | 回数据 2 个，659 和 498 KB/s |
| 只用 ut_metadata | 同上，不取 `.torrent` | 取回元数据，SHA1(info) 与 infohash 一致 |
| 只用 ut_metadata | 6.5GB 合集（45 个文件） | 10 片元数据拼接后 SHA1 校验通过 |
| 冷门合集找数据 | 同上，153 个 tracker | 可达的 4 个 peer 全是下载者，没有做种，拿不到数据 |
| 对照组 | Ubuntu 24.04.4 ISO | tracker 给 1 个、DHT 给 728 个；握手的 3 个真实 peer 全部回数据，99～139 KB/s |

其它观察：

- **tracker**：磁力里自带的动漫 tracker（`tr.bangumi.moe`、acgnx、anidex、acg.rip 等）从本机全部超时；`.torrent` 文件 announce-list 里的才有效。
- **DHT 可用**，给出的 peer 常比 tracker 还多。
- **监测节点占大头**：候选 peer 里七成以上的客户端名是 `Gopeed bt-scoring-source`、`bt-province-ratios`、`bt-region`，集中在江苏电信 IP 段、端口 200xx。它们只握手、不给数据，在任何种子里都出现。
- **dmhy 的 base32 磁力不是 v2**：它和「磁力链接 type II」里的 hex 是同一个 20 字节 v1 infohash 的两种写法。真正的 v2 磁力是 `urn:btmh:` 加 64 位 hex。
- **dmhy 的 `.torrent` 下载地址（`dl.dmhy.org`）本机不可达**。但同一资源常同时发布在 mikan，按 infohash 查详情会返回 mikan 的记录，它的镜像可达。
- 【实测】本机单集资源的 5 个做种者合计约 0.9 MB/s，该片码率 4.2 Mbps（约 0.53 MB/s），理论上够边下边播。

**结论：纯端上 BT 技术可行。** 协议链路（tracker、DHT、握手、元数据、piece 下载与校验）全部跑通。体验取决于那个资源有没有可达的做种者：热门单集可以，冷门合集可能一个都连不上。

### 0.7 本地播放代理化(11-25 第五轮,编译通过,待真机验收)

**用户真机反馈**:已缓存视频只有暂停/播放正常——进度条 -1:-1、拖不动、倍速失效(部分报"播放错误 code 801")、离线时选集失效。

**根因**:AVPlayer 以 fdSrc 直读裸 TS 时,HLS 引擎不参与——拿不到容器时长(显示 -1:-1)、seek/倍速能力缺失(801=能力不支持)、切集后回到在线地址(离线必失败)。§0.6 里 probe 页"能拖"其实碰的是同一批限制的另一面,结论记录有误。

**方案 = §5.5 规划过的路线 B 基建提前落地(通用做法,BT 边下边播直接复用)**:
- 新增 `common/LocalProxy.ets`:127.0.0.1 上 TCPSocketServer 起 HTTP 服务(端口 17821 起,占用则递增);把合并 .ts 按字节切成 4MB **伪分片**,生成伪 HLS 点播播放列表(时长按字节占比摊),`/seg{i}.ts` 支持 Range 请求按需读文件区间。AVPlayer 走 HLS 引擎 → 时长/拖动/倍速全部原生可用。
- `PlayerController.prepareLocal(key, path, durationMs, surfaceId)` 改为注册代理后 `player.url = http://127.0.0.1:.../index.m3u8`;不再直接 fdSrc。
- 时长数据:`HlsDownloader` 解析 EXTINF 合计(`estDurSec`),下载完成写 `Prefs.vdur_`;播放时 `VideoCache.estimateDurationMs()` 优先真实值,旧下载的集按 ~1.2MB/s 码率粗估,再兜底 25 分钟(伪列表的时长只是标度,seek 由引擎换算到字节,偏差不影响播放)。
- **选集失效修复**:`PlayerPage.switchTo` 现在自动判断目标集是否已下载——已下载继续本地播(离线可用),没下载回在线。

**待真机验收**:AVPlayer 访问 127.0.0.1 明文 HTTP 是否放行(§4.5 批次 5 的验证项之一,这次顺带验证)。若放行,本地播放应有时长、能拖、能倍速、离线选集可切;若不放行,退路是 fdSrc+估算时长+禁倍速的降级版。

### 3.1 布局与视觉规则（用户明确要求过，不要擅自改）

- **颜色**：页面底色 `#F1F3F5`；影视主色 `#3471D5`；漫画主色 `#8A5CF6`。

### 3.2 播放器（影视）

- `XComponent`（SURFACE）+ AVPlayer。视频宽高来自 `videoSizeChange` 事件。

### 3.3 直播

- 频道来自 iptv-org 两个列表的聚合。分组：英文分类映射成中文，央视排最前，其次卫视。

### 3.4 漫画

## 四、BT 内核（修正版与设计）

### 4.1 用户诉求与决策

- 雷达（AnimeGarden）资源**只有 `magnet:` 磁力链接，没有直链视频**。用户坚持**纯端上**实现「直接看和下载」，否决了外部下载器和自托管转码服务方案。
- 环境探查：本地有完整的 OHOS NDK 和 ohpm，但 ohpm 仓里没有现成的 BT 库；`aria2-ohos` 是鸿蒙 PC 上的命令行 hap，不能当库依赖；libtorrent 交叉编译要拖 boost 和 openssl 整条链。
- **技术路线**：纯 ArkTS 实现精简 BT 内核，不引入 native 编译链。

### 4.2 已落地文件

| 文件 | 内容 | 状态 |
|---|---|---|
| `datasources/bt/Bencode.ets` | bencode 编解码，用 class 承载节点 | 可用，需补一个带结束位置的解码（见 §4.3） |
| `datasources/bt/Magnet.ets` | magnet 解析（hex 和 base32 的 btih）、内置 tracker 列表 | 可用，需识别 `urn:btmh:` |
| `datasources/bt/Sha1.ets` | 纯 TypeScript SHA1，3 个标准向量含 1MB 数据通过 | 可用，真机速度没测过 |
| `scripts/btprobe/probe.mjs` | 旧原型：magnet 解析、tracker announce、bencode 解析 | 参考 |
| `scripts/btprobe/verify.mjs` | 旧原型：SHA1 标准向量验证 | 参考 |
| `scripts/btprobe/fullprobe.mjs`、`debug1.mjs`、`debug2.mjs` | 旧原型：握手、扩展握手、ut_metadata | **结论不可信**，消息 id 标错、长度前缀少 1 字节，见 §0.2 |
| `scripts/btprobe/swarmcheck.mjs` | 新的复核脚本，见下 | 本轮新增 |

`swarmcheck.mjs` 用法：

```bash
node scripts/btprobe/swarmcheck.mjs                      # 取 AnimeGarden 最新一个 v1 资源
node scripts/btprobe/swarmcheck.mjs <magnet|infohash> --data --dht --peers=50
node scripts/btprobe/swarmcheck.mjs <infohash> --ext --no-torrent      # 元数据只走 ut_metadata
node scripts/btprobe/swarmcheck.mjs --torrent=<.torrent 地址> --data   # 任意公开种子做对照
```

它依次做：取元数据、tracker announce（HTTP、HTTPS、UDP）、DHT `get_peers`、连 peer 握手、可选的 ut_metadata、可选地向 peer 要 1MB 数据测吞吐，最后输出汇总。

### 4.3 现有代码需要的修正

- **`Bencode.ets`**：`decode` 只返回节点树。ut_metadata 的 data 消息是「bencode 字典，后面紧跟原始 info 字节」，必须知道字典在哪里结束。要加一个 `decodePrefix(buf)`，同时返回节点和结束偏移。不要用 `indexOf('ee')` 去猜，旧的调试脚本就是这么做的，遇到 `i14e` 这种会找错位置。另外编码字典 key 时长度用的是字符串长度，遇到非 ASCII 的 key 会错，实际的 key 都是 ASCII，优先级低。
- **`Magnet.ets`**：hex 和 base32 都是 v1，现有处理是对的。要补两件事：遇到 `urn:btmh:` 明确报「暂不支持 v2 种子」；hybrid 种子同时带两种 xt，取 btih 那个。
- **`Sha1.ets`**：一次性对整块输入计算，校验 piece 够用。实现时优先用 `cryptoFramework.createMd('SHA1')`，原生实现会快很多，纯 JS 留作兜底。
- **`GardenClient.ets`**：现在丢掉了资源自带的 `tracker` 字段，也没有调用详情接口。两处都要补上（§4.4）。

### 4.4 引擎设计

**范围**：只做 v1 协议（BEP 3）。不做上传，不要求加密握手（MSE），不支持只有 v2 的种子。多文件种子支持选文件下载，合集里只下想看的集。

**流程**：雷达条目，取元数据，解析 `.torrent`，找 peer，握手，请求 piece，SHA1 校验，落盘，进离线库播放。

**元数据，分三级**

1. 调 `GET /detail/{provider}/{id}`，从 `detail.magnets[]` 里找 `.torrent` 的 HTTPS 直链下载。【实测】mikan、moe 的镜像可达。
2. 第一步失败，就向 peer 发扩展握手（BEP 10）和 ut_metadata 请求（BEP 9），拿到 info 字典后用 `SHA1(info) == infohash` 校验。【实测】单集和 6.5GB 合集都取回并校验通过。
3. 都失败，界面提示「暂时连不上任何做种者」，不假死。

取到的 `.torrent` 缓存到 `offline/bt/{infohash}.torrent`，下次直接用。构造磁力时要把资源自带的 `tracker` 字段拼上：`resource.magnet + resource.tracker`。

**找 peer**

- tracker：HTTP、HTTPS（BEP 3，`compact=1`）和 UDP（BEP 15）。把 `.torrent` 的 announce-list 和磁力里的 `tr=` 合并去重，`wss://` 的跳过。按 `interval` 定时重新 announce。
- DHT（BEP 5）：KRPC over UDP，`get_peers` 迭代查找。启动节点用 `router.bittorrent.com`、`dht.transmissionbt.com`、`router.stealth.si`、`dht.libtorrent.org`。【实测】可用。
- PEX（BEP 11）后置。

**连接管理**

- 同时保持 30 到 40 个连接。候选池随机打散，因为里面大半连不上或者是监测节点。
- 5 秒连不上就放弃。握手后 10 秒内既不发 bitfield 也不 unchoke 的，断开换人。
- 我方握手的保留字节里把扩展协议位置 1。发扩展握手时长度前缀等于 1 加扩展 id 加正文的字节数。
- 每个 peer 未完成的 request 不超过对方声明的 `reqq`，没声明就按 32。30 秒没回的 request 取消，换 peer 重发。

**下载调度**

- piece 内按 16KiB 分块请求。
- piece 的选择顺序：下载模式按文件顺序；边下边播模式先要播放点所在的 piece 和往后 30 秒的量，其余按稀有优先。
- 一个 piece 收齐就做 SHA1 校验，失败整块丢弃重下。
- 位图每个 piece 收完落盘一次，重启后续传。

**落盘**

- 目录用 `{filesDir}/offline/bt/{name}/`。多文件按偏移映射到种子的文件表。

**播放**

- 下完的文件用 `AVPlayer.fdSrc` 播。SDK 文档明确支持本地 MPEG-TS、MP4、MKV。
- 边下边播需要一个本地 HTTP 代理：`socket.constructTCPSocketServerInstance` 监听 `127.0.0.1`，支持 Range，把请求的字节范围从文件读出来回给 `AVPlayer.url`。还没下到的区间提高下载优先级。

**后台**：长时任务 `DATA_TRANSFER` 加进度通知，和 §5.6 共用。

**模块划分【设计】**

| 文件 | 职责 |
|---|---|

| `common/LocalProxy.ets` | 本地 HTTP 代理，和视频离线共用 |

### 4.5 实施步骤

1. **真机技术验证**（先做，半天到一天）：手机上 TCP 和 UDP 能不能连 tracker 与 peer；`cryptoFramework` 的 SHA1、AES 可不可用；本地 MKV 能不能用 `fdSrc` 播；AVPlayer 能不能访问 `127.0.0.1` 的 HTTP 服务。
2. `TorrentFile`、`Tracker`、`PeerWire`：能握手，能要到一个 piece 并校验通过。
3. `PiecePicker`、`BtSession`、落盘：单个文件能下完。
4. `Dht`、多文件选集、断点续传。
5. `BtDownloadManager`、离线库接入、后台长时任务。
6. 边下边播（本地代理）。

### 4.6 风险与未验证项

- **做种者可达性是最大变量**。【实测】热门单集有 5 到 7 个可达做种者；冷门合集一个都没有。界面要如实显示「已连接做种者 N 个」，不要只给一个转圈。
- 手机在 NAT 后面不可达，只能主动连别人。国内家庭宽带的做种者大多不可达。
- 所有数据都来自开发机所在的网络，手机网络下没测。
- **字幕**：动漫 MKV 多是内封字幕，AVPlayer 不渲染字幕轨，下回来很可能没有字幕。要么自己做字幕轨解析和叠加，要么换第三方播放内核。这是开工前要先定的事。
- **编码兼容**：AVPlayer 支持 H.264、HEVC 和 AAC。FLAC、TrueHD 这类音轨能不能播没验证。
- 没有可达做种者时任务会停在「寻找做种者」，要有超时和明确的提示。

## 五、离线观看方案（漫画 + 视频）

### 5.1 要解决的问题

用户要求：**已经下载的内容必须能看**。现在做不到。

| 内容 | 现状 | 离线时的表现 |
|---|---|---|
| 漫画详情 | `MangaDetailPage.aboutToAppear` 先请求 `detail()` 和 `chapters()`，成功才渲染 | 请求失败只弹一个 toast，页面空白，进不了任何章节 |
| 漫画阅读 | `MangaReaderPage.aboutToAppear` 先 `await MangaClient.chapters()`，之后才加载章节 | 网络异常没有人接，页面一直显示「加载中」。哪怕这一话整话都在本地也打不开 |
| 已下载标记 | 以偏好里的 `dl_` 标记为准，不核对文件 | 标成「已缓存」的章节可能缺图（§6 的 P0） |
| 影视 | 没有下载功能 | 没有离线内容 |
| 影视详情 | 和漫画一样完全依赖网络 | 从观看历史点进去是空白 |

图片缓存本身是好的，缺的是离线时的入口和元数据。

### 5.2 原则

1. **本地快照是离线时的唯一依据。** 下载过的漫画和剧集，在下载那一刻就把标题、封面、章节或集数列表存到本地。打开它不需要网络。
2. **网络只负责刷新。** 联网时在后台拉最新数据并覆盖快照；失败就继续用快照，界面标「离线」。
3. **「已下载」必须可信。** 文件齐全才标完成；启动时核对一遍标记和实际文件。
4. **一套下载体系。** 漫画、视频、BT 共用队列、后台任务和离线库界面，各自只实现「怎么下」。

### 5.3 总体结构【设计】

```
下载入口（详情页多选、雷达页）
  │
  ├─ 漫画下载（已有，即 DownloadManager）      图片
  ├─ VideoDownloadManager（新）               HLS 分片下载与合并
  └─ BtDownloadManager（新，§4.4）            BT
        │
   TransferScheduler（新）  并发预算、暂停恢复、网络变化、长时任务
        │
   OfflineStore（新）      离线快照（漫画、剧集的元数据）与已下载清单
        │
   离线库页面（新）  入口：我的；漫画 Tab 离线时；影视 Tab 离线时
        │
   MangaReaderPage / PlayerPage 读本地
```

### 5.4 漫画离线

改动集中在 `MangaCache`、`MangaDetailPage`、`MangaReaderPage`、`DownloadManager` 四处，先做。

**M1 漫画快照**

- 新增 `MangaCache.saveComicSnapshot(detail, chapters)` 和 `loadComicSnapshot(pathWord)`，存 `manga_cache/comic_{pathWord}.json`：名称、作者、简介、主题、更新时间、章节列表（uuid、name、index、size）、封面本地路径、保存时间。
- 封面下载到 `manga_cache/cover_{pathWord}.img`。
- 写入时机有两个：详情页加载成功后；`DownloadManager.enqueue()` 入队时。`enqueue()` 现在只收 `comicName`，要改成把 `detail` 和 `chapters` 传进去，调用点只有 `MangaDetailPage.confirmDownload()`。

**M2 详情页本地优先**

1. 先读快照。有就立刻用快照渲染，标记离线。
2. 再发网络请求。成功就合并章节、覆盖快照、取消离线标记；失败就保持快照。

离线时章节行分三种显示：已缓存、下载中（带进度）、未缓存（灰色，点击提示）。

**M3 阅读器去掉网络前置**

- `aboutToAppear` 里的章节列表改读快照，没有快照就先用空数组，不再等网络，直接 `loadChapterByUuid(uuid)`。网络的章节列表放到后台，结果到了再更新 `chapters`。
- `loadChapterByUuid` 的「本地直开」分支已经是零网络，不用动。
- 图片加载失败时显示「该页未缓存」的占位，这样下载到一半的章节也能看。
- 离线时预载下一话会失败，已经被 try/catch 吞掉，不用处理。

**M4 让「已缓存」可信**

- `MangaCache.downloadAll` 返回成功数和失败数。
- `DownloadManager.pump()` 只有失败数为 0 才标 `done`、写 `dl_` 标记；否则标 `failed`，保留进度。
- `DownloadManager.restore()` 启动时复核：对 `dl_` 里的每个 uuid 跑 `allCached()`，不完整的移出标记，之后可以重新下载。

**M5 离线库入口**

- 新页面 `OfflineLibraryPage`，路由名 `Offline`，顶部两段：漫画、影视。
  - 漫画段按快照列出，封面读本地文件，显示「已缓存 N 话，共 M 话」。点击进详情页。长按删除整部缓存。
  - 影视段见 V5。
- 「我的」里的「下载管理」改成「离线与下载」，里面分「已下载」和「下载中」两段，下载中就是现在 `DownloadsPage` 的内容。
- 漫画 Tab 和影视 Tab 监听网络状态。离线时顶部显示「离线模式」条，带一个「查看已下载」按钮。

**M6 网络状态**

- 新增 `common/NetWatch.ets`：`connection.createNetConnection()`，监听 `netAvailable` 和 `netLost`，维护 `online` 状态并通知订阅者。

### 5.5 视频离线

**格式现状**见 §1.4：HLS、`.ts` 分片、AES-128。`LiveSpeedTest` 里已经有解析 m3u8、流式拉分片的代码，可以参考。

**先在真机上验证两条路线，再定用哪条**

| | 路线 A：解密后合并成一个 `.ts` | 路线 B：本地 HTTP 代理 |
|---|---|---|
| 做法 | 下载时做 AES-128-CBC 解密，按顺序追加到一个 `.ts` 文件 | 分片原样保存。起一个只监听 `127.0.0.1` 的 HTTP 服务，把 m3u8 里的分片和 key 地址改写成本地地址 |
| 播放 | `AVPlayer.fdSrc = { fd, offset: 0, length }` | `AVPlayer.url = 'http://127.0.0.1:{port}/x.m3u8'` |
| 优点 | 一个文件，不依赖常驻服务，拖动稳定。SDK 明确支持本地 MPEG-TS | 不用写解密，TS 和 fMP4 分片都适用。BT 边下边播也需要它 |
| 缺点 | 要实现解密。fMP4 分片不能直接拼 | 播放时要有服务在跑。AVPlayer 访问回环地址的行为没验证过 |
| 适合 | 下载完离线看 | 边下边播 |

建议离线下载走 A，B 留给 BT 边下边播。前提是 A 的两个真机验证通过：合并后的 TS 能用 `fdSrc` 播放；`cryptoFramework.createCipher('AES128|CBC|NoPadding')` 解出来的首字节是 `0x47`。

**V1 下载器 `HlsDownloader`**

1. 拉播放地址。是 master 就选一档，默认最高，设置里可以改成优先标清。
2. 解析 media playlist：分片列表、`EXT-X-KEY`（METHOD、URI、IV，没给 IV 就用分片序号）、`EXT-X-MAP`。
3. 分片 4 到 6 个并发下载，用 `http.requestInStream` 流式接收，不整段放进内存。
4. 按序号顺序写文件，并发下完的先放进一个小的重排缓冲。加密的分片解密后写，去掉 PKCS7 填充。
5. 旁路文件记录每个分片是否写完、文件里连续写到了多少字节、码率、总时长。续传时先把文件截到连续的那一段，再往下下。
6. 全部写完标 `done`，写进离线清单。

**V2 队列 `VideoDownloadManager`**

- 结构照搬漫画的 `DownloadManager`：串行或 2 并发，状态 `queued`、`downloading`、`paused`、`done`、`failed`，快照写进偏好，重启后恢复。
- 任务粒度是一集。字段：`sourceId`、`vodId`、`routeIndex`、`episodeIndex`、`episodeName`、`url`、`segmentsDone`、`segmentsTotal`、`bytesDone`、`localPath`。
- 失败处理：播放列表拉不到，或者分片连续超时，自动换同一集的下一条线路重试一次，再失败标 `failed`。这和播放器的死链换线是同一个思路。

**V3 剧集快照**

- 入队时存 `VideoSnapshot`：标题、封面、简介、线路名、每一集的名称和地址。`VideoDetailPage` 按 M2 的方式本地优先。

**V4 播放本地文件**

- `PlayerController.prepareLocal(path)`：`fileIo.openSync` 之后设置 `fdSrc`。
- `PlayerNavParam` 加一个 `localPath`，有值就走本地。进度、选集、换线的逻辑不变，离线时只能选已下载的集。
- 页面关闭时关掉 fd。SDK 文档提醒：fd 交给 AVPlayer 之后不要再拿它做别的读写。

**V5 界面**

- 详情页加「选择下载」：集数网格多选，交互照搬漫画详情页。底部显示预估大小，确认后入队。
- 离线库的影视段按剧分组，组内是集列表，显示进度或「可离线播放」，点击进播放器，滑动删除。

**V6 流量与空间**

- 视频下载默认只在 Wi-Fi 下进行，用 `connection.getNetCapabilities()` 看 `bearerTypes`。移动网络要在设置里手动打开。
- 入队时和每个分片下载前检查剩余空间，用 `statvfs.getFreeSize()`。不足预估大小的 2 倍就暂停并提示。
- 下载前显示预估大小。单集 0.9GB 起，要让用户看到这个数。

**V7 mp4 直链**

- 现在的源都是 m3u8。mp4 等有需要再做，用 Range 请求下载即可。

### 5.6 后台下载

【现状】没有申请长时任务。退到后台一段时间后，网络请求可能被系统挂起，下载会停。

【设计】

- `module.json5` 的 `backgroundModes` 加上 `dataTransfer`。
- 新增 `TransferScheduler`：有任务在跑时调 `backgroundTaskManager.startBackgroundRunning(context, ['dataTransfer'], wantAgent)`，队列空了就取消。
- 用实时进度通知更新进度，间隔不超过 10 分钟。SDK 说明里写了：超过 10 分钟不更新进度，这个长时任务会被系统取消。
- 三个下载管理器共用这一个句柄。

### 5.7 存储管理

- 设置里显示漫画缓存和视频离线各占多少空间，遍历目录求和。
- 离线库里可以按漫画、按剧删除。漫画再加一个「清除未下载的阅读缓存」，就是阅读时顺带缓存下来的那些。
- 容量上限和自动清理后置。

### 5.8 实施顺序与验收

| 步骤 | 内容 | 规模 |
|---|---|---|
| 1 | M1 到 M4：漫画快照、详情页与阅读器本地优先、已缓存标记可信 | 中 |
| 2 | M5、M6：离线库页面、网络状态、离线入口 | 中 |
| 3 | §5.6 后台下载 | 小 |
| 4 | 视频路线 A 的真机验证 | 小 |
| 5 | V1 到 V4：HLS 下载器、队列、剧集快照、本地播放 | 大 |
| 6 | V5、V6：选择下载界面、离线库影视段、流量与空间 | 中 |
| 7 | BT 接入同一套队列和离线库（§4） | 大 |

验收时打开飞行模式逐条过：

1. 离线库里能打开已下载的漫画并翻话，没有报错弹窗。
2. 下载到一半的章节能打开，缺图的地方显示「未缓存」。
3. 已下载的视频剧集能播放、拖动、记住进度。
4. 下载中断网，任务显示「等待网络」，网络恢复后接着下，进度不丢。
5. 进程被杀后重进，队列恢复。完成的不重下，没完成的续传。
6. 手动删掉一张缓存图再重进，这一话不再显示「已缓存」。
7. 退到后台 10 分钟，下载还在进行。

## 八、开发约定与注意事项

1. **编译**：用户在 DevEco Studio 里自行编译验证，安装也由用户自己处理。命令行 hvigorw 也能编（§1.7），需要时可以用。
2. **ArkTS 严格模式**：不要写没有类型的对象字面量，要先声明 class 或 interface；`Length` 类型的值赋给 `number` 之前用 `Number(x ?? 0)` 转换；不解构，不对接口用展开运算符。更多见 §9。
3. **状态管理只用 V2**，不要引入 V1 的 `@State`、`@Prop`、`@Observed`。
4. **全局避让壳在 `Index.ets`**，子页面改 padding 无效。全屏态统一通过 `AppChrome.setFullscreen()` 切换，全屏页面的 `aboutToAppear` 设 `true`、`aboutToDisappear` 设 `false`。
5. **状态栏隐藏要在页面就绪之后调用**才可靠（`loadContent` 的回调加 `Index.aboutToAppear`），早期设置会被覆盖。
6. **桌面图标资源在 `AppScope/resources/base/media`**，不在 entry。生成脚本必须同时输出两处。
7. **布局规则不要擅自改**，见 §3.1。
8. **测网络的东西先写 Node 原型**，放在 `scripts/` 下，跑通再翻译成 ArkTS。BT 的全部结论都是这样得到的。
9. **git 仓库在 `github.com:Leeson-Wong/ani`（main 分支，2026-11-25 初始提交）**。注意：`build-profile.json5` 含签名密码密文，已加入 .gitignore 不入库——换机器克隆后要手动从本机拷回这份文件才能直接签名编译。
10. **对外请求里不要带个人信息**。探测脚本只发 infohash、peer_id 这类协议必需的字段。

## 九、踩坑速查

### 9.1 ArkTS 编译

| 现象 | 原因 | 做法 |
|---|---|---|
| `10605038 arkts-no-untyped-obj-literals` | 裸对象字面量没有对应声明的类型 | 先声明 interface，再写 `const x: T = {...}` |
| `10605999`、`10505001` | `Area` 的 `globalPosition.y`、`height` 是 `Length \| undefined` | `Number(x ?? 0)` |
| 各种严格模式报错 | 了解构、展开、`any` | 用显式的循环和拷贝；项目里的 `slice(0)`、`asObj`、`jStr` 就是为此准备的 |
| 枚举找不到 | 大小写写错 | `SafeAreaType.SYSTEM`、`BarPosition.End`、`SliderChangeMode.End`、`media.PlaybackSpeed.SPEED_FORWARD_*` |
| 属性名冲突 | 自定义状态变量叫 `offset`，和基础组件属性重名 | 换名字，比如 `listOffset` |
| 拿不到 context | 在普通 class 里调 `getContext()` | 页面里调，或者把 context 传进去 |
| `Kit '@kit.BackgroundTaskKit' has no corresponding config file` | 本 SDK 没打包这个 Kit | 直接从 `@ohos.resourceschedule.backgroundTaskManager` **默认导出**导入 |
| `Namespace 'media' has no exported member 'PlayDescriptor'` | API 26 改名 | 用 `media.AVFileDescriptor`；`AVDataSrcDescriptor` 同理 |
| `Property 'bundleName' does not exist on type 'BundleInfo'` | 本 SDK 的 BundleInfo 字段叫 `name` | `bundleManager.getBundleInfoForSelfSync(...).name` |
| `hasDefaultNet does not exist on NetConnection` | 它是模块级方法 | `connection.hasDefaultNet()`；实例上只有 `on/register` |
| `onLongPress` 不在 RowAttribute 上 | 长按要走手势 | `.gesture(LongPressGesture({repeat:false}).onAction(...))` |
| `listFile` 返回 Promise | 同步版有专门后缀 | `fileIo.listFileSync()`（同族还有 `accessSync/statSync`） |
| `'statvfs' is not exported from Kit` | CoreFileKit 里导出名不同 | `import { statfs } from '@kit.CoreFileKit'`（底层是 `@ohos.file.statvfs`） |
| `scrollBy` 参数报错 | Scroller 的方法签名是两个数字 | `scroller.scrollBy(dx, dy)`，不是对象 |
| `Property 'scroller' does not exist on ListAttribute` | Scroller 要走构造参数 | `List({ space: 0, scroller: this.x })` |
| Column 报 `no maxLines` | `maxLines` 是 Text 的属性 | 限宽用 `constraintSize({ maxWidth })`，截断放 Text 上 |

### 9.2 系统接口

| 现象 | 原因 | 做法 |
|---|---|---|
| `player.videoWidth` 不存在 | API 26 移除了 | 监听 `videoSizeChange` 事件 |
| 页面销毁阶段 `scroller.currentOffset()` 返回 undefined → 读属性 crash | NavDestination 退出时组件已解绑 | 滚动位置不要在 `aboutToDisappear` 里查 scroller;用 `onDidScroll` 随时记 lastY |
| 全屏后底部还有一条白边 | `setWindowSystemBarEnable([])` 管不到手势条 | 再调 `setSpecificSystemBarEnabled('navigationIndicator', false)` |
| 改了子页面的 padding，位置没变 | 避让壳在 `Index` 上 | 走 `AppChrome.setFullscreen()` |
| 弹出的提示栏跑到屏幕中间 | `Stack` 默认居中 | `Stack({ alignContent: Alignment.TopStart })` |
| 手势层把滚动吃掉了 | 全屏透明的点击层抢了手势 | 把点击事件挂到图片上，不加透明层 |
| 用商用机装不上 target 24 的包 | 设备静默拒绝 | target 保持 26.0.0 |

### 9.3 布局

| 现象 | 原因 | 做法 |
|---|---|---|
| 卡片里的文字溢出到旁边的格子 | 卡片容器没有限定宽度 | 容器 Column 加 `.width('100%')` |
| `FlowItem` 的 `width('100%')` 变成了整页宽 | WaterFlow 里百分比参照的对象不对 | 改成固定宽度的卡片，按行手排（§3.1） |
| 分类 chips 和列表重叠 | 列表没有减去 chips 的高度 | 列表用 `layoutWeight(1)` |
| 标题栏/返回键区域和 loading 态露白 | 只给了内层内容灰底，`NavDestination` 本身是系统白底 | 带 `.title()` 的页面，`NavDestination` 也要 `.backgroundColor('#F1F3F5')`（全屏黑底页同理给黑）。11-25 已补：漫画详情、影视详情、影视源管理 |

### 9.4 构建与安装

- `targetSdkVersion` 不能是 24。SDK 26 打出来的 target 24 的包，商用机会静默拒绝安装。
- Rust 绑定在商用机上缺 `napi_reject_deferred`，napi-rs 的异步用不了。小说时期是靠手写的最小 NAPI 绑定绕过去的，详见 `README.md` 的「历史遗留」。
- `build-profile.json5` 里有签名材料的本机路径和口令密文，换机器要重新生成。

### 9.5 hdc

见 §1.7 的表格。最常踩的是 MSYS 把 `/data/local/tmp` 改写成 Windows 路径。

### 9.6 播放与数据源

| 现象 | 原因 | 做法 |
|---|---|---|
| 播放器报 `5411007` | 资源不存在，多半是 CDN 死链 | 换线路 |
| 直播测速全是 0 或都一样 | 只拉了 m3u8 索引 | 拉真实的 `.ts` 分片 |
| 漫画页面顺序是错的 | 接口返回的 `contents` 是乱序的 | 按 `words[]` 还原 |
| 章节顺序反了 | 按响应顺序排了，或者多做了一次反转 | 按 API 的 `index` 升序 |
| 漫画接口返回裸 `error` | 缺请求头，或者域名漂移了 | 补上四个请求头，换 BASE |
| AVPlayer fdSrc 直读裸 TS:时长 -1、拖不动、倍速报 801 | TS 无容器索引,HLS 引擎不参与 | 经 LocalProxy 伪装 HLS 点播(§0.7);duration 用 EXTINF 合计 |

### 9.7 BT 协议

| 事项 | 说明 |
|---|---|
| 消息长度前缀 | 等于「消息 id 加正文」的字节数。旧脚本少算了 id 那 1 个字节，导致对端断连 |
| 消息 id | 0 CHOKE、1 UNCHOKE、2 INTERESTED、3 NOT_INTERESTED、4 HAVE、5 BITFIELD、6 REQUEST、7 PIECE、8 CANCEL、9 DHT_PORT、20 EXT |
| `upload_only` | 1 表示对方已下完、只做种 |
| 扩展握手 | 长度前缀等于 1 加扩展 id 加正文。`m` 字典里是对方各扩展消息的 id |
| ut_metadata | 取元数据不需要先被 unchoke。data 消息是「bencode 字典加原始字节」，字典的结束位置要由解析器给出 |
| infoHash 校验 | v1 的 infoHash 就是 info 字典原始字节的 SHA1 |
| 监测节点 | 客户端名含 `bt-scoring`、`province-ratios` 的，只握手不给数据，尽早断开 |
| `wss://` tracker | 是 WebTorrent 的信令服务器，端上不支持，跳过 |
